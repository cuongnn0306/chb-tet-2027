# RET-001: return request (E10, REQUESTED stage only)

Task: `RET-001` · agent claude · immutable report per attempt.

RET-001 only lets the **Admin** open a return request for goods that were really delivered, and lets the Admin read it.
Receiving into Pending Inspection (RET-002), inspection (RET-003), restock (RET-004), damage (RET-005), revenue adjustment
(RET-006), commission adjustment (RET-007, COM-005) and exchange (RET-008) are separate tasks and are **not** implemented or
pre-empted here. A request moves no stock, refunds nothing, changes no commission and does not change the order.

## Approved semantics taken from the specs

1. A request is a `returns` row (`status = REQUESTED`) with `return_items` lines (`quantity > 0`). Statuses are exactly the five of
   §3.24/§11. The code is generated by the database.
2. A line references a real `order_items` row of the request's order; the product is **taken from the order line**, never from
   the caller. The order must be `COMPLETED`.
3. The reason is required (non-blank after trimming).
4. The cumulative quantity requested for a line may never exceed what was delivered (the counting rule below).
5. The request is one atomic RPC, audited (`audit_row_change` on both tables, actor = the Admin, reason "Yêu cầu trả hàng").
6. Returned stock goes to Pending Inspection and is not sellable (AGENTS §4, PRD §20.1): a request creates **no**
   `inventory_movements` / `inventory_balances` / `inventory_reservations` change, selects no batch (`batch_id` and
   `inspection_result` stay NULL) and creates no revenue or commission effect.
7. Rows are never hard-deleted, `TRUNCATE` is refused, frozen identity fields cannot change, and the §11 edges are the only
   allowed status changes (the guard already enforces them so later tasks cannot skip a state). No RPC performs a transition.
8. Clients have no INSERT/UPDATE/DELETE privilege; the only door is the `SECURITY DEFINER` RPC `request_return()`.

## Design

- `public.returns` / `public.return_items`: TECH §3.24/§3.25 columns (+ `UNIQUE (return_id, order_item_id)`), CHECKs for status
  values, positive quantity, non-blank reason ≤ 500, clean REQUESTED rows.
- `private.returnable_quantity(order_item_id)`: the counting rule (one definition).
- `private.returns_guard` / `private.return_items_guard` (+ truncate refusal): code generation, REQUESTED-only inserts, COMPLETED
  order only, line belongs to the order, product equals the line's product, no batch/verdict at creation, cumulative cap,
  frozen fields, §11 edges only, no delete.
- RLS: Admin reads `returns`; `return_items` follow their return; `anon` has nothing; no client write privileges.
- `public.request_return(order_id, items jsonb, reason)`: validates role, reason, 1..50 distinct lines, shapes, order state,
  line membership, delivered and cap; inserts return + lines atomically; returns the return and its lines. Errors are Vietnamese
  `P0001` / `42501` messages already handled by `describeDbError`.
- Domain `src/domain/returns/request.ts`: labels, §11 edges, `returnableQuantity`, `validateReturnRequest` (optional counting
  inputs for the cap), `parseReturnQuantity`, `canRequestReturn`, `isOrderReturnable`. Limits mirror the RPC.
- Service `src/services/returns.service.ts`: `request` (validates, one RPC), `returnableOrder` (order lines with what is left),
  `listForOrder`, `get`. Same loose-client pattern as `transfers.service.ts` because the generated types lack the new tables
  until the pipeline regenerates them.
