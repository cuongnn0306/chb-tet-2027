## Findings

### P1 — Receiving-account normalization accepts malformed identifiers

`supabase/migrations/20261002040000_sepay_payload_validation.sql` uses
`private.sepay_norm` for both bank names and account identifiers. It deletes every
character outside `[a-z0-9]`, and the processor accepts numeric account values.

With the synthetic configured account `1234567890`, both the string
`12345.67890` and the numeric value `-1234567890` pass the account check. A local
SQL reproduction returned `UNMATCHED` for both, proving they reached order
matching rather than being stopped with `NEEDS_REVIEW`.

SePay documents `accountNumber` as a string. Validate the account identifier
separately from the bank name and preserve identifier semantics, including leading
zeros. Reject malformed types/values. Do not remove arbitrary punctuation or
Unicode characters to turn malformed input into a configured account. Any
accepted formatting or gateway aliases need an explicit, documented rule.

### P1 — Accepted ID representations bypass deduplication

The processor accepts numeric IDs and digit-only strings but stores their text
without canonicalization. The synthetic numeric ID `987654321076514` and string
`0987654321076514` both returned `UNMATCHED`; two `payment_events` rows were
stored for the same integer. Neither call returned `DUPLICATE`.

Both event deduplication and payment provider references use this text, so their
unique constraints cannot identify these representations as the same transaction.
The reproduction used an unknown order and created no payments; it does not
claim an observed production double credit.

SePay documents an integer ID. Either enforce that documented representation or,
if numeric strings remain supported, validate and canonicalize to one key before
both deduplication layers. Preserve the raw payload for traceability. Account for
already stored noncanonical keys if changing an applied migration's behavior.
